# Forward Test — Phase Tracker

Measure whether Signavex's daily picks actually outperform the market over time. Cheaper and more honest than a multi-year backtest because it uses **real** picks generated by the live system on real market days, with no paid historical data needed.

> **Why now:** Quantback (the backtest) is data-bound — Polygon free tier is 2 years EOD, fundamentals/news/macro are not historically replayable. A forward-test sidesteps every one of those constraints by capturing today's picks and grading them as time passes. The catch is patience — the first 30-day verdict is 30 days out.

> **Status:** scoping. No code yet.

## Decisions to confirm before FT1

These shape the rest. **User decision needed:**

1. **What counts as a "pick"?**
   - Option A: only candidates above the live surfacing threshold (currently 0.45)
   - Option B: every scored candidate (capture all, filter later via SQL)
   - **Recommendation:** B. Storage is cheap, future analysis (does score X actually beat score Y?) needs the full distribution.

2. **Entry price assumption?**
   - Option A: scan-day close (assumes you bought at end of the day picks were surfaced — implausible since picks are produced overnight)
   - Option B: next-trading-day close (you saw the pick in the morning, bought by end of day)
   - **Recommendation:** B. Conservative and matches what a real user would do.

3. **Horizons?**
   - Recommend: 30d, 90d, 180d, 365d. Enough granularity to spot whether the picks have edge in the short or long term, without exploding the table.

4. **Visibility?**
   - Pro-only with aggregate stats? Public landing-page proof point ("our picks beat SPY by X% over 90 days, on N picks since Y")?
   - **Recommendation:** Pro-only initially; promote to public landing once we have ≥6 months of data and the numbers don't embarrass us.

5. **Backfill from historical scans?**
   - We already have a `ScanCandidates` table with daily candidate rows going back to launch. Retroactively populating `PickOutcomes` from those — using the historical OHLCV cache to fill in 30/90/180 prices — gives us instant signal instead of 30+ days of waiting.
   - **Recommendation:** yes — FT3 phase below. Cheap; high information return.

**Exit criteria:** every daily scan produces N PickOutcome rows with EntryDate/EntryPrice filled in. Empty horizon columns until FT2 fires.

## FT2 — Outcome tracker: nightly job fills in horizon prices
- [ ] **FT2.1** New Functions timer trigger (`PickOutcomeEvaluator`) — runs daily, e.g. midnight UTC
- [ ] **FT2.2** Query: rows where `EntryDate + horizon ≤ today` AND that horizon's columns are null
- [ ] **FT2.3** For each, fetch the ticker's close on the target date + SPY's close on the target date — both from the historical OHLCV cache (Q3 work pays off)
- [ ] **FT2.4** Compute `TickerReturnPct`, `SpyReturnPct`, `Outperformance = ticker - spy`. Persist.
- [ ] **FT2.5** Tests: synthetic OHLCV, verify rows graduate from null to populated as time advances

**Exit criteria:** running the timer with mock "today" produces correct outcomes for sample picks, with all four horizons filling in over time as the date crosses each threshold.

**Exit criteria:** running the backfill against a fresh DB produces a populated `PickOutcomes` table with as much horizon data as the available history allows. Effectively "instant analytics."

## Notes
- FT1 + FT3 + FT4 minimum viable is the fastest path to actually answering "are our picks any good." FT2 is what keeps the data fresh going forward; without FT3, FT2 means waiting 30 days for the first answer.
- Cost of FT2 nightly: nearly zero. Each evaluated pick = 0–2 cache hits (ticker close + SPY close on that date) — historical OHLCV cache means no Polygon calls after warmup.
- Survivorship bias note: a delisted ticker won't have OHLCV at the target horizon. Those rows should be flagged "delisted/missing" rather than treated as a 100% loss — that's a real edge case to handle in FT2.
